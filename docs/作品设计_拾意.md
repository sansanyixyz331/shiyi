# 作品设计 · 拾意 Pickup

> GOSIM Agentic App 黑客松 2026「意图即应用」参赛作品设计。
> 路径：**应用层（Nautilus）**；宿主 **Rinx**；场景：**即时消息**。

---

## 1. 选题与理由

**题眼**：官方说"意图不一定来自你说的话——它可能藏在一封邮件、一条消息、一个时间点或一次状态变化里"。

**选「消息里的意图」，四条理由**：

1. **正中题眼**：意图来自**消息正文**，而不是用户对着 AI 下指令 —— 这是"意图即应用"最纯粹的样子。
2. **宿主天然贴合**：Rinx 本身就是消息应用，**数据（聊天）和场景（应用）在同一个地方**，
   不需要额外编造数据源，也不容易被质疑"事实从哪来"。
3. **用上我们的长处**：**长期记忆**——不只处理这一条，还记住你的老规矩并据此改变建议。
   这正好是官方范例（购物链路）没有的一层。
4. **纯应用层、不依赖设备改造**：桌面参考宿主即可完整演示，不引入额外的设备侧依赖。

## 2. 用户故事（分两个场景）

**桌面端 = 工作场景 · 消息来源「邮件」**（把邮件原文作为一条消息投递，非接入邮箱服务）：

| # | 邮件 | 拾到 | 卡片 |
|---|---|---|---|
| 1 | 客户邮件："周四上午来我司谈一下续约" | 时间=周四上午 · 地点=对方公司 · 类型=会面 | 识别卡 → 确认 → 会面准备卡；**记忆：周四上午已有例会 → 冲突提醒** |
| 2 | 供应商邮件："下周一送货，收货人写你" | 时间=下周一 · 类型=收货 | 识别卡 → 确认 → 收件提醒卡 |
| 3 | 内部邮件："方案评审改到下周三" | 时间=下周三 · 类型=评审 · **状态变化（"改到"）** | 识别卡 → **更新已有卡片** |

**手机端 = 日常场景 · 消息来源「聊天 / 家庭群」**：

| # | 消息 | 拾到 | 卡片 |
|---|---|---|---|
| 4 | 家庭群："下周三我得去趟深圳" | 时间=下周三 · 地点=深圳 · 类型=出行 | 识别卡 → 确认 → 出行准备卡；**记忆：你一贯坐高铁，已按高铁筛** |
| 5 | "帮我把那个快递寄到上海" | 地点=上海 · 类型=跑腿 · **指代"那个"未解析** | 识别卡 + **追问卡**（不猜，问清是哪个） |
| 6 | 朋友群："周末约球，老地方" | 时间=周末 · 地点=老地方（白名单外） | 识别卡 + **追问卡**（地点不全会问，不瞎补） |

## 3. 识别要素（五类信号）

1. **时间词** —— 今天/明天/后天/下周X/周X/X月X号/时刻；
2. **地点词** —— 城市白名单 + "去(趟)X"句式；
3. **承诺 / 请求** —— "我得""帮我""记得""别忘了"；
4. **状态变化** —— "改到""推迟""取消了"（**这是官方点名的一类**，用来更新已有卡片）；
5. **指代** —— "那个""上次说的"→ **一律不猜，出追问卡**。

## 4. 作品形态与链路（复赛三形态）

同一套设计，做成**三种交付形态**（详见 [`STRUCTURE.md`](../STRUCTURE.md)）：

| 形态 | 位置 | 链路 |
|---|---|---|
| **① 脚本应用**（复赛主提交） | 根 `bundle/` | 读绑定房间消息（或输入一句话）→ 点一条 → **当场造一张卡** → 确认 → **真发回群** |
| **② L0 卡片包** | `apps/shiyi-card/bundle/` | 五屏链接（见下） |
| **③ 系统 app** | `octos/` | 卡钉到**快览屏**；钉卡即**念一遍**、到点**再弹再念**；在卡的对话里叫助手 → **原地改卡** |

**② 卡片包那五屏（详细链路）**：
1. **识别卡** —— 拾到什么（时间/地点/类型）+ **来源芯片**（哪个房间、什么时候）
2. **追问卡** —— 拿不准的字段（指代、非白名单地点）当面问
3. **方案卡** —— 摆出老规矩筛过的候选
4. **记忆卡** —— 命中哪条偏好、因此改变了什么；可编辑
5. **完成卡** —— 做了什么、**数据来源逐一标注**

## 5. 数据来源对照（no-facts 声明）

| 卡片上的事实 | 来源 | 处理方式 |
|---|---|---|
| 消息原文 / 房间 / 时刻 | `message_text` / `message_meta` / `system_clock` | **原样引用** |
| 时间解析 | 本地规则（后续可换模型） | 标 `confidence`；拿不准 → `needs_user`，交人 |
| 地点 | 城市白名单 + 原文 | **非白名单不补全**，只标低置信 |
| 天气 / 班次（若做） | 真实服务 API | **必须标注来源与查询时刻** |
| 记忆命中 | **本机记忆文件** `.local-state/memory.json` | **显式写出**"命中哪条、改变了什么" |

**绝不**：编造执行结果、编造服务状态、把"建议"写成"已完成"。
代码层已落实：`src/intent_card.py` 每张卡都带 `facts[]`（每个事实标明 `from`），
以及 `disclaimer` 字段声明"未查询任何外部服务"。

> **留档（2026-09-27）**：第 5 屏曾印「行程已排 / 日历已加 / 提醒已设」，三件一件没真做 ——
> 违反本条红线。已改为「一件真做了（写记忆）、两件明说没动」，详见 `README.md` §8.1。

## 6. 差异化：长期记忆

| 层 | 官方范例（aircon） | 拾意 |
|---|---|---|
| 输入 | 外部服务状态 | **消息正文**（用户没在发指令） |
| 记忆 | 单次行程状态 | **跨会话长期偏好**（不坐飞机/惯坐高铁/周三下午不排事） |
| 存储 | 宿主内部 | **本机 JSON 文件** `.local-state/memory.json` —— 可打开、可核验（`src/memory_store.py`） |
| 效果 | 走完链路 | **偏好改变建议**（同样是去深圳，别人给三个方案，它只给一个） |
| 控制 | 逐步确认 | 逐步确认 + 可编辑偏好 + 可撤回 |

## 7. 实现路径

**识别核心（已在作品内）**：`src/intent_card.py` 把"消息 → 识别 → 卡片语义 → 来源标注 → 记忆命中"跑通；每张卡都带 `facts[]`（每个事实标明 `from`）+ `disclaimer`。记忆层为**真读写**：`src/memory_store.py`（本机 JSON 文件、零权限）。

**L0 卡片包（②形态）**：按官方要求**不手写 L0** —— 走 Image-to-AppCard 工作流生成 `page.card` + `page.data.json` + `kit/`（组件名为自动生成的哈希名），再由服务逻辑补数据 / 状态 / 事件语义。

**交付**：在参考宿主跑通 → 抓真实截图 → 盖章 / 门禁 / 审查包 → 发布（复现见 [`SUBMISSION.md`](../SUBMISSION.md) §D）。

## 9. 已知限制与对策

| 项 | 说明 / 对策 |
|---|---|
| 消息数据隐私 | 全程本地解析；卡片显式标注来源；不引入外部服务即无外传 |
| 手写 L0 不可行（组件名是哈希） | 走 Image-to-AppCard 工作流生成；`apps/shiyi-card/bundle/page.card` 由工作流产出 |
| 目标设备平台 | **Windows 桌面官方参考宿主**与**安卓真机（小米13 / Rinx 宿主）**两端均完成端到端验证；`listing.platforms` 如实声明 `["windows","android"]`（安卓侧的运行载体是 Rinx，官方 Rinx 赛道即"本地导入 bundle"这一路径） |
| 模型可替换 | 作品**不绑定任何模型提供方**，换模型作品零改动 |
| 车次为演示样例 | `src/shiyi_flow.py` 的班次为样例（`source: sample`），接真实票务前不当事实 |
