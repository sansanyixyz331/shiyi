# 作品设计 · 拾意 Pickup

> GOSIM Agentic App 黑客松 2026「意图即应用」参赛作品设计。
> 路径：**应用层（Nautilus）**；宿主 **robrix2**；场景：**即时消息**。

---

## 1. 选题与理由

**题眼**：官方说"意图不一定来自你说的话——它可能藏在一封邮件、一条消息、一个时间点或一次状态变化里"。

**选「消息里的意图」，四条理由**：

1. **正中题眼**：意图来自**消息正文**，而不是用户对着 AI 下指令 —— 这是"意图即应用"最纯粹的样子。
2. **宿主天然贴合**：Rinx 本身就是消息应用，**数据（聊天）和场景（应用）在同一个地方**，
   不需要额外编造数据源，也不容易被质疑"事实从哪来"。
3. **能吃到我方长处**：**长期记忆**——不只处理这一条，还记住你的老规矩并据此改变建议。
   这正好是官方范例（购物链路）没有的一层。
4. **不依赖刷机**：纯应用层，桌面参考宿主即可完整演示，**规避我方刷机线的不确定性**。

## 3. 识别要素（五类信号）

1. **时间词** —— 今天/明天/后天/下周X/周X/X月X号/时刻；
2. **地点词** —— 城市白名单 + "去(趟)X"句式；
3. **承诺 / 请求** —— "我得""帮我""记得""别忘了"；
4. **状态变化** —— "改到""推迟""取消了"（**这是官方点名的一类**，用来更新已有卡片）；
5. **指代** —— "那个""上次说的"→ **一律不猜，出追问卡**。

## 4. 卡片链路

**最小可交（5 卡）**：
1. **识别卡** —— 拾到什么（时间/地点/类型）+ **来源芯片**（哪个房间、什么时候）
2. **待确认卡** —— 三个动作：确认 / 改一下 / 不管它
3. **追问卡** —— 拿不准的字段（指代、非白名单地点）当面问
4. **执行结果卡** —— 做了什么、**数据来源逐一标注**
5. **记忆卡** —— 命中哪条偏好、因此改变了什么；可编辑

**完整版（10 卡）**：+ 冲突提醒、偏好编辑、来源追溯、撤回/撤销、周期回顾。

## 5. 数据来源对照（no-facts 声明）

| 卡片上的事实 | 来源 | 处理方式 |
|---|---|---|
| 消息原文 / 房间 / 时刻 | `message_text` / `message_meta` / `system_clock` | **原样引用** |
| 时间解析 | 本地规则（后续可换模型） | 标 `confidence`；拿不准 → `needs_user`，交人 |
| 地点 | 城市白名单 + 原文 | **非白名单不补全**，只标低置信 |
| 天气 / 班次（若做） | 真实服务 API | **必须标注来源与查询时刻** |
| 记忆命中 | **本机记忆文件** `.local-state/memory.json` | **显式写出**"命中哪条、改变了什么" |

**绝不**：编造执行结果、编造服务状态、把"建议"写成"已完成"。
代码层已落实：`src/intent_card.py` 每张卡都带 `facts[]`（每个事实标明 `from`），
以及 `disclaimer` 字段声明"未查询任何外部服务"。

> **留档（2026-09-27）**：第 5 屏曾印「行程已排 / 日历已加 / 提醒已设」，三件一件没真做 ——
> 违反本条红线。已改为「一件真做了（写记忆）、两件明说没动」，详见 `README.md` §8.1。

## 6. 差异化：长期记忆

| 层 | 官方范例（aircon） | 拾意 |
|---|---|---|
| 输入 | 外部服务状态 | **消息正文**（用户没在发指令） |
| 记忆 | 单次行程状态 | **跨会话长期偏好**（不坐飞机/惯坐高铁/周三下午不排事） |
| 存储 | 宿主内部 | **本机 JSON 文件** `.local-state/memory.json` —— 可打开、可核验（`src/memory_store.py`） |
| 效果 | 走完链路 | **偏好改变建议**（同样是去深圳，别人给三个方案，它只给一个） |
| 控制 | 逐步确认 | 逐步确认 + 可编辑偏好 + 可撤回 |

## 7. 技术路线（两段式）

**段一 · 开发期验证（本周，已起步）**
- 用 Python 把"消息 → 识别 → 卡片语义 → 来源标注 → 记忆命中"跑通 —— **已完成，可运行**：
  `python src/intent_card.py`
- 记忆层已从"代码常量"升级为"**真读写**"：`src/memory_store.py`（本机 JSON 文件，零权限）。
- 目的：先把**识别什么、标注什么、记忆怎么生效**定死，产出**卡片的目标结构**。

**段二 · 交付期（走官方正路）**
1. 按 `bundle/page.card` 的形状出**设计图**（我方有生图能力）；
2. 走 **Image-to-AppCard 工作流**生成正式 `page.card` + `page.data.json` + `kit/`
   （**官方明确要求不要手写 L0**，组件名是自动生成的哈希名）；
3. 写服务逻辑（L0 数据/状态/事件语义）；
4. 在参考宿主 `card-host` 跑起来 → **抓真实截图** → 盖章 / 门禁 / 审查包；
5. 签名 → 提交（`bundle/` + 源码引用）。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| **本机无 Rust 工具链**，WSL 被 ARC 线占用 | 先确认 `hub`/`card-host` 能否在 Windows 构建；不能则**另开独立编译环境**（守零交叉） |
| 手写 L0 不可行（组件名是哈希） | **必须走 Image-to-AppCard 工作流**；`bundle/page.card` 只作结构目标 |
| 三个 lock 文件钉的 revision 与本地 checkout 不一致 | 以 `native-runtime.lock.json` / `native-apps.lock.json` 为准，不擅自升级共享 checkout |
| 一周时间紧 | 保底先做**5 卡**；10 卡是加分不是底线 |
| 消息数据隐私被质疑 | 全程本地解析；卡片显式标注来源；不引入外部服务即无外传 |
