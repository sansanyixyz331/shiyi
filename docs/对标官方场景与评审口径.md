## 一、官方 12 场景 → 我方落「即时消息」

官方赛道一的 12 个场景：邮件、即时消息、日历、天气、新闻、音乐、视频、财经、导航、购物与物流、写作与创作、系统与设备。
**「拾意」落在「即时消息」** —— 理由：本作品的全部输入都是**别人发来的一句话**（群里、聊天里），输出是**回到聊天里的回执**。这是"信息进来 → 意图成形 → 结果回去"的完整闭环，正是即时消息场景的核心。

| | 我方实现 | 核验 |
|---|---|---|
| 输入 | 一句自然语言（"下周三去深圳""周末买显示器"） | `bundle/page.card` 的 `read` 屏 |
| 识别 | 时间 / 地点 / 类型三类信号，**抽不到就留空、绝不编造** | `cards/shiyi-01-read/page.data.json` |
| 输出 | 回执发回聊天（`matrix.send_message`） | `bundle/bindings.json` + `rinx/证据/房间消息_关键事件.json` |

> ⚠️ **不跟"最挤的选题"撞**：对手里邮件 3 家、日历 2 家、写作 2 家（2026-10-05 全量扫描，36 仓）。我方选的即时消息**只有自己**。

## 二、官方两个硬点 → 逐条对齐

官方评审口径原话（研讨课逐字稿）：
> "最佳 agentic 是从**真实的输入到执行，看到检验的结果**。只生成界面都不算完成任务，**必须能跑**，**能展示失败状态**，你不能给一个静态的概念稿。"

| 硬点 | 我方对应 | 在哪 |
|---|---|---|
| **① 必须能跑** | 官方参考宿主 `card-host` 内**真渲染**（515×1115 帧，逐像素可查）；Rinx 真机导入 → Run 跑通 | `build/verify_flow.py` · `build/_evidence/` |
| **② 必须展示失败状态** | **两个失败态**：未签名被拒 / 摘要不符被拒 —— 宿主**拒绝且零渲染**（fail-closed），抓图 + 宿主日志 + 演示片 ③ 段 | `build/_evidence/neg_*.png` · `build/_video/shiyi-walkthrough.mp4` |
| **③ 真实输入→执行→结果可检验** | 识别出的时间/地点 → 记忆命中 → 只给合规方案（"不坐飞机→只给高铁"）→ 回执真发出 | `04_plan` 屏 + `rinx/证据/` |

**关键设计（不是"静态概念稿"的证据）**：卡片不是画上去的图——`page.card` 是**声明式源码**，`page.data.json` 是**真实数据**，两者经官方 hub 校验（`hub check PASSED`）；打开首屏时 `bindings.json` **真触发**三条宿主调用。**卡面每一个字都来自数据，不是硬编码。**

## 三、官方加分项 → 我方「接了 AI 总线」

官方原话：
> "如果**跨应用联动**或**写到日历里面、能把调用总线（AI 总线）**，这也算是**最佳技术加分**。"

**我方 `bundle/bindings.json` 三条调用 = 就是"总线"，不是单点功能**：

| 总线动作 | 服务 | 说明 | 全场占比（10-05 扫描） |
|---|---|---|---|
| **读（房间）** | `matrix.read_messages` | 读**绑定房间**的最近消息，点一条直接造卡 | **3 / 36 队** |
| **读（助手）** | `octos.session.history` | 读设备助手的会话（你之前说过的） | **2 / 36 队** |
| **问** | `octos.turn.start` | 向助手提问、取回答 | 10 / 36 队 |
| **写** | `matrix.send_message` | 把回执真发进聊天房间 | **3 / 36 队** |

⇒ 我方接的是**"读房间 + 读助手 + 问 + 写"四段总线**（每段都是全场稀缺格），**不是单点接一个 AI**。
**关键**：三条全部走**官方契约**（`AI-SERVICES.md`），不碰 provider / key；宿主没有该服务时，每条都在 `when X.is_ok` guard 后**不求值**，卡片照常渲染。

## 四、两种形态（同一件作品，两副面孔）

「拾意」提供**两种官方承认的形态**，覆盖"看"与"玩"：

| | **形态一：L0 卡片**（主提交） | **形态二：脚本应用**（现场造卡） |
|---|---|---|
| 位置 | `bundle/`（`page.card` + `bindings.json`） | `apps/shiyi-live/bundle/`（`main.splash`） |
| 能力 | 打开即渲染五屏 + 三条总线调用 | **读绑定房间消息 → 点一条 → 当场长出卡**（另挂 助手会话 / 模型 两条；**四条能力全默认关、失败必兜底**） |
| 优势 | **全场唯二**用 L0 卡片形态的队（实质唯一） | **能玩**：改一下 / 确认 / 再来一张，三种状态真实交互 |
| 共享 | 识别口径、长期记忆 schema、"意图→卡片"内核 —— **同一套** | 同左 |

**为什么两种都给**：官方赛道一明确承认**两种交付形态**（进程应用 / App Card）。我方**两种都做了**——卡片证明"形态独特性"，脚本应用证明"真实可交互"。**这正是官方问答里"不要静态概念稿"的正面回答。**

> 形态二跑在 **Windows 宿主（Rinx）** ⇒ 其 `manifest.integrity.bundle_blake3` 为 **Windows 平台计算值**；卡片形态（主提交）交 **Linux 评测** ⇒ 留 **Linux 值**。摘要分平台是上游已知问题（#75，我方 PR #79 已修）。**谁运行它，就用谁那一侧的 hub 盖章。**
