# 生成器 —— 「意图即卡」（v2）

> 状态：**跑通（2026-10-04）**。从一条消息出发，「识别 → 组装 → 排版 → **自评修订** →
> 渲染 → 过官方门禁」全链自动走通，**一条命令**。这是复赛「任务自动化 + 技术突破」
> 的地基，也是本项目从「一张卡」到「一个会造卡的机器」的落地。

## 一、它做什么

```
build/pipeline.py            ← 一条命令
   │
   ├─ 生成   build/gen_l0.py            意图 -> bundle
   │            └─ 内含：{意图识别 → 适配器取模板 → 组装行 → 动态排版 →
   │                     几何自评 → 有问题就改 → 再出}
   ├─ 渲染   build/shot_bundle.py       card-host --remote 抓真实帧进 bundle
   └─ 门禁   WSL 里的官方 Linux hub      stamp + check（判定环境是 Linux）
```

## 二、六样能力，全部真装进去了

| # | 能力 | 来源 | 落点（本仓实物） |
|---|---|---|---|
| ① | **意图识别引擎** | 本仓 `src/intent_card.py` | 生成器的大脑：when/where/类型/记忆/追问/来源 |
| ② | **长期记忆层** | 本仓 `src/memory_store.py` | 生成时**读真文件** (`.local-state/memory.json`)，替掉写死的 `DEFAULT_PREFS` |
| ③ | **契约 + 适配器** | 三三Claw 接口层那套 | `INTENT_ADAPTERS`：一种意图一条声明；**加新意图不改核心** |
| ④ | **反思 → 自评修订回路** | 三三Claw 的反思回路 | `selfcheck()` + `revise()`：排完**自评几何**（越界/超带/超格），有问题就改再出 |
| ⑤ | **自动化工具链** | 我们一贯做法 | `build/pipeline.py`：生成→自评→渲染→门禁，一条命令出报告 |
| ⑥ | **应用造应用** | 33OS「智能体即应用」的认知 | 本文件自身：**一个 app，从一句话造出另一个 app 包** |

> ②③④⑤ 是"把已有的能力换个环境落"——引擎、记忆、反思、工具链都是我们本来就有的；
> 落点才是新的（OctoSense 的 L0 契约）。⑥ 是立意：**交的不是一个 app，是一个会造 app 的 app。**

## 三、四个"不是模板"的实据

跑 `python build/pipeline.py --samples --out build/_gen`：

| 消息 | 识别 | 生成结果（同一引擎，各不相同） |
|---|---|---|
| 下周三我得去趟深圳 | trip | 3 字段 + **3 条记忆行** + 问「排成一次行程」 |
| 明天下午三点跟老王在杭州碰一下 | meeting | 3 字段 + **无记忆行** + 问「定成一次会面」 |
| 帮我把那个快递寄到上海 | errand | **2 字段（无时间）** + 追问「那个」指代 + 问「把它办掉」 |
| （超长）…参加供应商会议顺便见三个客户… | trip | **原文不被切**：卡片自己**长高**（quote 78px/3 行），下方全部下移 |

三张都：`l0-bindings-lint` **0 error**；官方 Linux `hub check` **PASSED**。

## 四、自评回路干过什么（真实战绩）

- **样例 02**：`row_when` 文案 26 字 > 组件容量 24 → 自评报出 → 自动缩短 → 第二轮干净。
- **超长消息**：不让原文溢出，而是**改布局** —— quote 带宽随原文行数长高，下方节点全部下移，
  最后自评确认"内容底 632 < 动作带 740"，一轮即干净。
- 自评过程**逐轮落盘** `<out>/review.json` —— 这就是复赛要的「复现证据」里的
  "看自己的结果并改进"。

## 五、为什么是"生成"而不是手写

官方文档（App Design Flow）自己就写着：**不要手写 L0**。手写是初赛阶段的权宜（也是我们
吃透规则的方式）；复赛要的「任务自动化」，就是把这条手工链路换成机器链路——而这些
**能力我们本来就有**，缺的只是把它们接到 L0 的产出上。这就是"能力换环境"。

## 六、两个关键的工程坑（都记在技能里）

1. **L0 遍地 `{}`** ⇒ 模板必须用 `string.Template`（`$var`），f-string / `str.format` 会炸。
2. **`hub stamp` 与 `hub check` 必须同一平台**：Windows 的 hub 与 Linux 的 hub 对同一
   bundle 算出的 `bundle_blake3` **不同**（与 #75 同源）⇒ 最终判定一律走 WSL。

## 七、边界（照实）

- 现在做的是**「结构化意图 → 组件库组装」**，不是"任意意图 → 任意 UI"。官方自己的
  App Studio（ADR 0006）也分里程碑。
- 覆盖**单屏确认卡**；五屏流转（`cards/`）仍手写，生成器尚未接管。
- 生成器**不产出提交物**：产出在 `build/_gen/`（已 ignore）。`bundle/`（冻结的初赛提交物）
  与 tag `v0.3.1` **一字节不动**。

## 九、视觉自评（第二块：看渲染出来的那一帧）

几何自评是在"还没画"时算坐标；**视觉自评**是在"已经画完"之后真去数像素——
`build/visual_review.py` 用 WSL 里的 ImageMagick 取**逐行 / 逐列灰度剖面**，
把明显暗于背景的行判为"有内容的行"，据此抓：内容贴到画布边（=被裁）、
底部动作带没画出来、画布近乎空白（元素丢了）。

分工很清楚：**几何自评管布局精确性（坐标），视觉自评管渲染结果对不对（像素）**。

实测：三张卡的视觉块数 **6 / 7 / 8**（各不相同），与结构层的差异**对得上**——
两个层面互相印证。

## 十、五屏生成（第一块：不只第一屏，五屏都生成）

`build/gen_screens.py` 把一条消息生成**整套五屏**：

| 屏 | 内容从哪来（真生成） |
|---|---|
| 01-read | 识别出的字段 + 记忆命中 + 追问 |
| 02-ask | **`questions`** 就是它的两个问题；选项按缺口类型生成 |
| 03-plan | 按意图出样例方案（**明确标注"样例"**，不谎称查过） |
| 04-memo | 旧值取自**真记忆文件**，新值取自本次识别 |
| 05-done | 回执三行，按**真实发生的事**分列 |

五屏共用一套**垂直流布局引擎**（块从上往下排、动作带钉底部）——加/改一屏不动引擎。
每屏还产出 `service-actions.json`（每个控件对应什么事件，供 Agent 切换）。

实测：一条消息 → 五屏，**五屏全部渲染成功、视觉自评全 CLEAN**
（块数 6/4/8/6/7）；read 屏 bundle 过官方 `hub check` **PASSED**。
